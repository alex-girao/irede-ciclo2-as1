TDD na Prática com JUnit 5 questões Nível Básico a Avançado

Pratique o ciclo Red → Green → Refactor escrevendo testes e código Java reais. Cada questão apresenta um problema a ser resolvido com os conceitos deste capítulo: anotação @Test, assertivas (assertEquals, assertTrue, assertFalse) e o ciclo do TDD. Leia o enunciado, tente resolver por conta própria e depois revele a solução para conferir.

0/5
reveladas
1)
RED — Escrever o Teste que Falha
Básico
Antes de existir qualquer código de produção, escreva o teste de unidade testSomar para um futuro método Calculadora.somar(int a, int b), que deverá retornar a soma dos dois números.
Requisitos
  • Use a anotação @Test no método de teste
  • Chame Calculadora.somar(2, 3) e guarde o resultado em uma variável
  • Use assertEquals(5, resultado) para verificar o valor esperado
Solução
@Test public void testSomar() { int resultado = Calculadora.somar(2, 3); assertEquals(5, resultado); }
Resultado ao rodar o teste
✗ FALHOU testSomar() cannot find symbol: class Calculadora
💡 Esse é o comportamento esperado na etapa Red: a classe Calculadora ainda não existe, então o teste falha (ou nem compila). É esse "vermelho" que orienta o próximo passo da implementação.
2)
GREEN — Implementar o Mínimo para Passar
Básico
Agora escreva o código de produção mínimo necessário para que o teste testSomar da questão anterior passe.
Requisitos
  • Crie a classe Calculadora
  • Implemente public static int somar(int a, int b)
  • Não adicione nada além do necessário para o teste passar (essa é a filosofia do Green)
Solução
public class Calculadora { public static int somar(int a, int b) { return a + b; } }
Resultado ao rodar o teste
✓ PASSOU testSomar() Tests run: 1, Failures: 0
💡 No Green, o objetivo não é escrever o código "perfeito" — é fazer o teste passar da forma mais simples possível. A qualidade do código é tratada depois, na etapa Refactor.
3)
Ciclo Completo — Verificar Número Par
Intermediário
Aplique o ciclo completo Red → Green para um novo método Calculadora.ehPar(int numero), que deve retornar true quando o número for par e false quando for ímpar.
Requisitos
  • Escreva (Red) dois testes: um para número par e outro para número ímpar
  • Use assertTrue(...) e assertFalse(...) nas assertivas
  • Implemente (Green) public static boolean ehPar(int numero) usando o operador %
Solução
// RED — testes escritos primeiro @Test public void testEhParComNumeroPar() { assertTrue(Calculadora.ehPar(4)); } @Test public void testEhParComNumeroImpar() { assertFalse(Calculadora.ehPar(7)); } // GREEN — implementação mínima public static boolean ehPar(int numero) { return numero % 2 == 0; }
Resultado ao rodar os testes
✓ PASSOU testEhParComNumeroPar() ✓ PASSOU testEhParComNumeroImpar() Tests run: 2, Failures: 0
💡 Escrever mais de um caso de teste (par e ímpar) ajuda a garantir que a implementação realmente trata a regra de negócio, e não apenas "engana" um único caso.
4)
REFACTOR — Javadoc e Testes de Borda
Intermediário
Refatore a classe Calculadora (a mesma do exercício 2, com o método somar), adicionando documentação e cobrindo casos de borda, sem quebrar os testes já existentes.
Requisitos
  • Adicione um comentário javadoc descrevendo o método somar
  • Escreva um novo teste testSomarComNumerosNegativos
  • Escreva um novo teste testSomarComZero
  • Todos os testes (o antigo e os novos) devem continuar passando
Solução
public class Calculadora { /** * Retorna a soma de dois números inteiros. */ public static int somar(int a, int b) { return a + b; } } @Test public void testSomarComNumerosNegativos() { assertEquals(-5, Calculadora.somar(-2, -3)); } @Test public void testSomarComZero() { assertEquals(4, Calculadora.somar(4, 0)); }
Resultado ao rodar os testes
✓ PASSOU testSomar() ✓ PASSOU testSomarComNumerosNegativos() ✓ PASSOU testSomarComZero() Tests run: 3, Failures: 0
💡 Refatorar não significa apenas "arrumar" o código de produção — também vale reforçar a suíte de testes com casos de borda (negativos, zero, limites) para dar mais confiança à implementação.
5)
Ciclo Completo — Validador de Senha
Avançado
Aplique o ciclo completo Red → Green → Refactor para um método Validador.senhaValida(String senha), que deve retornar true apenas quando a senha tiver 6 caracteres ou mais.
Requisitos
  • Red: escreva testes para uma senha válida (6+ caracteres) e uma inválida (menos de 6)
  • Green: implemente a versão mínima de senhaValida usando senha.length()
  • Refactor: extraia o número 6 para uma constante TAMANHO_MINIMO, mantendo os testes verdes
Solução
// RED — testes escritos primeiro @Test public void testSenhaValidaComSeisCaracteres() { assertTrue(Validador.senhaValida("123456")); } @Test public void testSenhaInvalidaComMenosDeSeisCaracteres() { assertFalse(Validador.senhaValida("123")); } // GREEN — implementação mínima public class Validador { public static boolean senhaValida(String senha) { return senha.length() >= 6; } } // REFACTOR — número mágico extraído para constante public class Validador { private static final int TAMANHO_MINIMO = 6; /** * Retorna true se a senha tiver ao menos TAMANHO_MINIMO caracteres. */ public static boolean senhaValida(String senha) { return senha.length() >= TAMANHO_MINIMO; } }
Resultado ao rodar os testes (após o Refactor)
✓ PASSOU testSenhaValidaComSeisCaracteres() ✓ PASSOU testSenhaInvalidaComMenosDeSeisCaracteres() Tests run: 2, Failures: 0
💡 Perceba que o Refactor não adicionou nenhum comportamento novo — apenas melhorou a legibilidade do código (constante nomeada em vez de número mágico). Os mesmos testes, sem nenhuma alteração, continuam validando a nova versão.
