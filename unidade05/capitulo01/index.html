Conceito de Teste de Software Verificação & Validação

Teste de software é o processo de verificar se uma aplicação se comporta conforme os requisitos definidos. Essa verificação pode incluir:

Correção funcional do código Validação de comportamentos esperados Identificação de falhas ou inconsistências Avaliação de desempenho, segurança e usabilidade
Tipos de Teste de Software 4 Níveis

Cada tipo de teste tem um propósito específico. A seguir, os mais utilizados:

🧩 Teste de Unidade: testa métodos ou funções individuais, isoladas do restante do sistema.

🔗 Teste de Integração: verifica a interação entre dois ou mais módulos do sistema.

💻 Teste de Sistema: avalia o funcionamento do sistema completo e integrado.

✅ Teste de Aceitação: valida se o software atende aos requisitos do usuário ou cliente final.

Classificações dos Testes Funcional & Não Funcional

Além dos tipos, os testes podem ser classificados pelo seu objetivo principal:

Funcionais: validam funcionalidades, comportamentos e lógica do sistema.

Não funcionais: avaliam aspectos secundários como performance, escalabilidade, usabilidade, segurança.

Exemplo: um teste que verifica se o sistema calcula um desconto corretamente é funcional. Já um teste que mede o tempo de resposta ao acessar uma página é não funcional.

O Ciclo de Vida de um Bug 6 Etapas

Um bug é qualquer falha, erro ou comportamento inesperado em um sistema que compromete seu funcionamento ou desrespeita os requisitos definidos. Nem todo bug é uma falha crítica — mas todo bug é uma oportunidade de melhoria.

Identificação → Registro → Análise → Correção → Validação → Fechamento ↻ (retorna para Identificação, caso reabra)

Exemplo prático: usuário digita "João" no campo de nome, mas o sistema exibe "Jo@o" ao salvar.

EtapaO que aconteceu
IdentificaçãoRelato do erro pelo próprio usuário.
RegistroTicket #248 criado no Jira.
AnáliseEncoding de caracteres incorreto.
CorreçãoAjuste de UTF-8 no backend.
ValidaçãoTeste automatizado confirma a correção.
FechamentoBug "Resolvido" e liberado em nova versão.
Introdução ao TDD Test-Driven Development

TDD (Test-Driven Development) é uma metodologia ágil de desenvolvimento que prioriza testes desde o início. Obedece 3 etapas:

RED — escreva um teste que falha ↓ GREEN — implemente o mínimo para passar no teste ↓ REFACTOR — melhore o código mantendo os testes verdes ↻ (novo teste, novo ciclo)

devmedia.com.br — Test-Driven Development (TDD): simples e prático

Exemplo Prático com TDD dobrar(int)

Cenário: criar uma função para dobrar um número.

RED — o teste falha porque Utilitarios.dobrar() ainda não existe:

@Test public void testDobrarNumero() { int resultado = Utilitarios.dobrar(2); assertEquals(4, resultado); }

GREEN — agora o teste passa, validando a funcionalidade:

public class Utilitarios { public static int dobrar(int valor) { return valor * 2; } }

REFACTOR — podemos, por exemplo, aplicar boas práticas como documentar o método com javadoc e criar testes adicionais para valores negativos ou limite.

Estrutura Básica de um Teste JUnit
@Test public void testDobrarNumero() { int resultado = Utilitarios.dobrar(2); assertEquals(4, resultado); }

@Test: anotação de teste.

Método de Teste: public void testDobrarNumero() {...}

Assertivas (assert): assertEquals(4, resultado);

🚀 Curiosidades sobre Testes de Software e TDD
🐛
A origem da palavra "bug"
Em 1947, a programadora Grace Hopper encontrou uma mariposa presa em um relé do computador Harvard Mark II, causando uma falha. O inseto foi colado no relatório com a anotação "first actual case of bug being found" — um dos registros mais famosos do termo.
🔁
TDD nasceu (ou renasceu) com o Extreme Programming
Kent Beck popularizou o Test-Driven Development no final dos anos 1990, como parte da metodologia ágil Extreme Programming (XP), redescobrindo uma prática que já era usada décadas antes no desenvolvimento de software.
✈
O JUnit nasceu em um voo
Kent Beck e Erich Gamma criaram a primeira versão do JUnit durante um voo transatlântico em 1997, para ajudar desenvolvedores Java a escrever testes de unidade de forma simples e padronizada.
💬
"Testes mostram a presença de bugs, não a ausência"
Frase atribuída ao cientista da computação Edsger Dijkstra: testes podem provar que existem erros, mas nunca provam com certeza que um programa está livre de falhas.
🔺
A Pirâmide de Testes
Um modelo popular sugere ter muitos testes de unidade (rápidos e baratos), menos testes de integração e poucos testes de interface/aceitação (lentos e caros) — equilibrando cobertura, velocidade e custo de manutenção.
💯
100% de cobertura não é sinônimo de "sem bugs"
É possível ter cobertura total de código e ainda assim ter bugs: cobertura mede quais linhas foram executadas pelos testes, não se todos os cenários e combinações possíveis foram verificados.
