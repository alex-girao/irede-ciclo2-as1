01
ConectarRemoto git remote
Você inicializou um repositório local com git init. Agora precisa conectar ao repositório remoto que foi criado no GitHub (https://github.com/empresa/projeto.git) e enviar a branch main.
O que fazer
Adicionar o remoto como "origin"
Verificar que foi adicionado corretamente
Enviar a branch main para o remoto
Comandos
# Adicionar o remoto $ git remote add origin https://github.com/empresa/projeto.git # Verificar $ git remote -v origin https://github.com/empresa/projeto.git (fetch) origin https://github.com/empresa/projeto.git (push) # Enviar main e configurar tracking $ git push -u origin main Branch 'main' set up to track remote branch 'main' from 'origin'.
git remote add origin <url> vincula o repositório local ao remoto. O -u no push configura o tracking, permitindo usar git push e git pull sem argumentos futuramente.
02
FetchEInspecionar git fetch
Sua equipe pode ter feito push de commits novos. Antes de integrar, você quer baixar sem mesclar e inspecionar o que mudou, comparando com sua branch local.
O que fazer
Baixar atualizações do remoto sem mesclar
Ver o histórico dos commits remotos
Comparar a branch local com a remota
Comandos
# Baixar sem mesclar $ git fetch origin remote: Enumerating objects: 8, done. From https://github.com/empresa/projeto a3f8c12..d9e2b47 main -> origin/main # Ver commits remotos $ git log --oneline origin/main # Comparar local vs remoto $ git diff main origin/main # Se aprovado, mesclar $ git merge origin/main
git fetch baixa para o cache local (origin/main) sem tocar na sua branch. Você inspeciona com calma e só mescla quando tiver certeza. Mais seguro que git pull em repositórios críticos.
03
DesfazerCommitPublico git revert
O commit b7e2d09 introduziu um bug em produção e já foi publicado. Outros membros da equipe já baixaram esse commit. Desfaça com segurança sem reescrever o histórico.
O que fazer
Criar um commit que desfaz o commit problemático
Publicar o fix no remoto
Comandos
# Criar commit que desfaz o commit problemático $ git revert b7e2d09 # Abre o editor para mensagem do commit de revert # (ou use -m para pular o editor) $ git revert b7e2d09 --no-edit [main f4d3e12] Revert "fix: corrige validação do formulário" Date: ... 1 file changed, 5 deletions(-) # Publicar o revert $ git push To https://github.com/empresa/projeto.git b7e2d09..f4d3e12 main -> main
git revert cria um novo commit que inverte as mudanças do commit especificado. O histórico fica com ambos os commits (o original e o de revert), o que é auditável e seguro. Use --no-edit para aceitar a mensagem padrão.
04
ResetLocal git reset
Você fez 2 commits locais (ainda não publicados) e quer "desfazê-los" mas manter as alterações dos arquivos no staging para poder reeditar e recomitar com mensagens melhores.
O que fazer
Desfazer os 2 últimos commits mantendo as mudanças no staging
Verificar o resultado
Comandos
# --soft: desfaz commits, mantém tudo no staging $ git reset --soft HEAD~2 # Verificar: as mudanças estão no staging prontas para commit $ git status Changes to be committed: modified: src/Service.java new file: src/Model.java # Agora crie commits melhores $ git commit -m "feat: adiciona Model e Service com tratamento de erros"
HEAD~2 significa "2 commits antes do atual". --soft preserva as mudanças no staging. Use --mixed (padrão) para manter no working dir mas limpar o staging. Use --hard apenas se quiser descartar TUDO (irreversível!).
05
StashWorkflow git stash
Você está trabalhando em feature/login com mudanças não commitadas. Um colega pede para você revisar o código na branch feature/pagamento. Use stash para guardar seu trabalho, revisar e voltar.
O que fazer
Guardar o trabalho atual com descrição
Trocar para feature/pagamento
Voltar para feature/login e recuperar o trabalho
Comandos
# Guardar com descrição útil $ git stash push -m "WIP: implementando validação de email" Saved working directory and index state On feature/login: WIP: implementando validação de email # Trocar de branch $ git switch feature/pagamento # ... revisar o código ... # Voltar e listar os stashes $ git switch feature/login $ git stash list stash@{0}: On feature/login: WIP: implementando validação de email # Recuperar o trabalho $ git stash pop On branch feature/login Changes not staged for commit: modified: src/auth/LoginService.java
Use git stash push -m "descrição" para identificar facilmente o stash depois. git stash list mostra todos os stashes. git stash pop aplica o mais recente e remove da pilha.
06
CriarTag git tag
O projeto chegou à versão 2.0. Você precisa marcar o commit atual com uma tag anotada v2.0 e publicar essa tag no repositório remoto.
O que fazer
Criar tag anotada com mensagem
Ver a tag criada
Publicar a tag no remoto
Comandos
# Criar tag anotada no commit atual $ git tag -a v2.0 -m "Release v2.0 — Sistema de pagamentos completo" # Ver as tags $ git tag v1.0 v2.0 # Ver detalhes da tag $ git show v2.0 tag v2.0 Tagger: Ana Silva <ana@empresa.com> Date: ... Release v2.0 — Sistema de pagamentos completo # Publicar a tag no remoto $ git push origin v2.0 # Ou publicar todas as tags de uma vez: $ git push origin --tags
Tags não são enviadas automaticamente com git push. Você precisa publicar explicitamente com git push origin v2.0 ou --tags para todas. Tags anotadas (-a) são preferidas para releases pois incluem metadados.
07
RecuperarComReflog git reflog
Você acidentalmente executou git reset --hard HEAD~3 e perdeu 3 commits importantes que não haviam sido publicados. Recupere os commits perdidos usando o reflog.
O que fazer
Verificar o reflog para encontrar o hash anterior ao reset
Recuperar os commits perdidos
Comandos
# Ver o histórico do HEAD (incluindo o estado antes do reset) $ git reflog a3f8c12 HEAD@{0}: reset: moving to HEAD~3 f7c3d49 HEAD@{1}: commit: feat: adiciona relatório PDF e2b1a38 HEAD@{2}: commit: feat: cria modelo de dados d9e2b47 HEAD@{3}: commit: chore: configura banco de dados # O estado antes do reset era HEAD@{1} (hash f7c3d49) # Opção 1: reset para o estado anterior $ git reset --hard f7c3d49 HEAD is now at f7c3d49 feat: adiciona relatório PDF # Opção 2: criar branch para inspecionar antes $ git checkout -b recuperacao f7c3d49
O reflog é o "plano de emergência" do Git: registra todas as movimentações do HEAD nos últimos 90 dias. Mesmo após um --hard destrutivo, os commits ficam acessíveis pelo hash no reflog. Salva vidas!
08
PushForcado --force-with-lease
Você fez rebase de uma branch local (privada, apenas sua) e agora precisa atualizar o remoto, mas o push normal é rejeitado. Use o push forçado seguro que protege contra sobrescrever trabalho de outros.
O que fazer
Entender por que o push foi rejeitado
Usar a variante segura de force push
Comandos
# Push normal é rejeitado após rebase $ git push ! [rejected] feature/login -> feature/login (non-fast-forward) # Motivo: histórico reescrito diverge do remoto # --force: sobrescreve o remoto (perigoso se outros estiverem usando) $ git push --force # --force-with-lease: mais seguro — falha se alguém fez push enquanto você rebased $ git push --force-with-lease To https://github.com/empresa/projeto.git + d9e2b47...f7c3d49 feature/login -> feature/login (forced update)
--force-with-lease verifica se o remoto está no mesmo estado que você tinha quando fez o fetch. Se alguém fez push entre o seu fetch e force push, o comando falha, protegendo o trabalho dos outros. Sempre prefira --force-with-lease ao --force simples.
09
RevertMultiplosCommits git revert
Um conjunto de 3 commits consecutivos (abc1234 até def5678) introduziu uma feature com bugs. Todos já foram publicados. Desfaça todos os 3 de forma segura, sem criar um commit de revert para cada um.
O que fazer
Reverter um intervalo de commits com um único revert
Criar apenas um commit de revert para todos
Comandos
# Reverter um intervalo de commits # Sintaxe: git revert <hash-mais-antigo>..<hash-mais-recente> $ git revert abc1234..def5678 # Para criar apenas UM commit de revert para todos (não um por commit): $ git revert abc1234..def5678 --no-commit # Isso deixa tudo no staging... $ git commit -m "revert: remove feature de notificações com bugs" # Publicar $ git push
A sintaxe A..B indica "do commit após A até B". O flag --no-commit acumula todos os reverts no staging sem commitar, permitindo criar uma única mensagem de commit descritiva para toda a operação.
10
WorkflowProfissional completo
Simule o dia de trabalho completo de um desenvolvedor: começar com o estado atual do remoto, desenvolver uma feature, publicar, e lidar com uma situação de desfazer.
Passo a passo
Atualizar main com o último estado do remoto
Criar branch de feature
Desenvolver e commitar
Publicar a branch e criar PR (via GitHub)
Após merge do PR, limpar branches locais e remotas
Marcar release com tag
Dia de trabalho completo
# 1. Começo do dia: atualizar main $ git switch main $ git pull # 2. Criar feature branch $ git switch -c feature/dashboard-v2 # 3. Desenvolver $ git add . $ git commit -m "feat: redesign do dashboard principal" $ git add . $ git commit -m "feat: adiciona gráficos em tempo real" # 4. Publicar branch para revisão (PR) $ git push -u origin feature/dashboard-v2 # → Abrir Pull Request no GitHub/GitLab # 5. Após merge do PR: limpar $ git switch main $ git pull # baixar o merge do PR $ git branch -d feature/dashboard-v2 $ git push origin --delete feature/dashboard-v2 # 6. Marcar release $ git tag -a v3.0 -m "Release v3.0 — Dashboard v2" $ git push origin v3.0
Este é o fluxo real de um desenvolvedor profissional. Pontos-chave: sempre atualize main antes de começar, trabalhe em branches, use PRs para revisão, limpe branches após merge e marque releases com tags anotadas. Esse ciclo se repete para cada feature/fix.
